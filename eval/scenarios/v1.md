# Scenario set v1 (Track E item 6)

`v1.json` holds 19 scenarios for `app/eval/runner.py` (`load_scenarios`). The
`Scenario` format has a `notes` field, so each scenario's rationale is also in
the JSON; this table is the owner-review view. No `llm` block is set, so every
scenario uses the runner and `make_llm` defaults. Models are the owner's call
(E9).

All scenarios use postal code M5V3A8, the only code the snapshots cover.

"Offered" is `deal_source().fetch_current_deals(postal, restrictions)` against
the snapshot: the deals the user would actually be served, out of all deals in
the snapshot. `app/tests/test_eval_scenarios.py` recomputes it and fails if this
table drifts from the code.

Budget class (weekly scenarios only), by budget / (household_size x num_meals):
tight under 3, mid 4 to 10, generous over 10. The class is a hyphen-separated word of the
scenario name.

## Needs owner review

- **Kosher scenarios offer 0 deals** (`week1016-kosher-mid-hh2`,
  `week1016-kosher-nutfree-generous-hh4`, `seed27-kosher-mid-hh1-m1`). The
  committed snapshots have `not_kosher = NULL` for every product (no kosher
  decision had been made at capture), and NULL fails closed. These scenarios
  therefore cannot exercise the meat-with-dairy rule until a snapshot with
  kosher-labelled products exists; today they measure behaviour with an empty
  deal pool. Recapturing a snapshot after kosher labelling would fix this.
- `sparse5` scenarios are deliberately scarce (1 to 5 deals); the vegan and
  gluten-free ones are offered a single deal.
- In names, a `-m1` / `-m2` suffix marks a non-default `num_meals` (absent
  means the default, 7). `-hhN` is household size.
